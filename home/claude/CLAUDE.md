# Harness

Claude Code's skills, settings, and this file are generated by home-manager from ~/dotfiles, a public repo. Change the harness by editing that repo, from whichever project the friction showed up in.

- A skill is `~/dotfiles/home/claude/skills/<name>/SKILL.md`. `~/.claude/skills` is a symlink farm from the nix store; never write there.
- The flake sees tracked files only, so a new file must be `git add`ed before a build or switch can pick it up.
- Apply with `home-manager switch --flake ~/dotfiles` or `sudo darwin-rebuild switch --flake ~/dotfiles`; the hostname picks the config, so no `#name`.
- From a session in another project, changes to ~/dotfiles stop at writing files: print the `git add`, `git commit`, and switch commands for the user instead of running them.
- Keep project names, work hostnames, and key filenames out of that repo and its commit messages.
- The Bash tool runs bash 5 from nixpkgs (`CLAUDE_CODE_SHELL` in claude.nix), whatever the login shell is. `sed` is GNU sed, so `sed -i` takes no `''` suffix.

# Commits and pull requests

A repository's own contributing guide wins over this section where it sets how commits are kept.

One commit per change. What may happen to the branch depends on its stage:

- **No pull request yet**: fold work into the commit it belongs to (amend, or fixup and autosquash), without asking.
- **Draft, not yet reviewed**: reshape your own commits the same way, as needed.
- **Under review** (out of draft, or reviewed): the branch only grows. A review fix is a new commit, usually `git commit --fixup=<sha>` of the commit it corrects, never of a `fixup!` or `amend!`; address-review sets out when it is an `amend!` or its own commit. Amend or fold an unreviewed fixup of your own in place, then push it with `git push --force-with-lease`. Do not otherwise amend, rebase, or force-push on your own. A moved base stays unless it conflicts or the change needs what landed; then say so and name `git rb` and `git push --force-with-lease`.
- **Before merge**: the author squashes the fixups onto the same base, `git rebase -i --autosquash $(git merge-base HEAD origin/<base>)`, and pushes with `git push --force-with-lease`, so the diff the reviewers approved stays the same. Catch up with the base only when it conflicts or the repository requires an up-to-date branch. Repositories that squash-merge skip this. When the review is settled, say the branch is ready for that.

An instruction to keep a pull request to one commit, from an issue for example, covers the draft stage only.

# Steps and questions for the user

Steps left for the user to run, such as landing, pushing, applying a configuration, a check on another machine, or a cleanup, go out as the exact commands in the order to run them, one fenced block each. Name the directory or machine when it is not the current one. Never stand in for a command with "the usual steps" or an alias named without its invocation: the user runs them from the reply, not from memory.

Ask a question once. When the user answers something else and does not take it up, do not ask it again, in the reply or in a closing prompt; say once that it is still open, then leave it until they come back to it.

# Comments and commit messages

A comment is for whoever reads the code as it stands: a constraint, an invariant, a non-obvious trade-off, or why a value is what it is. A commit message is for whoever reads the change: why it was needed and why this approach. If a sentence still matters once the commit is out of view, it is a comment; if it only explains the patch, it is the message. Skip comments that restate the code.

# Causes

A fix that removes the symptom is not finished until the cause is named. Before calling a bug fixed, say in one line what caused it and what evidence says so — a log line, a `git log -S` hit, a failing test, a repro. Where there is no evidence for the step below, stop and call it a hypothesis rather than filling the gap with something plausible. Keep going down while the evidence holds, and stop at a cause that can actually be changed. When the same failure turns up a second time, the cause to name is why the first fix let it through.

# Showing changes

Every time you change files, show the diff itself, not only a summary of it. In the desktop app, open the diff pane for files in the session's folders; for anything else, paste `git diff` in a `diff` code block. Show it before asking the user to commit or push.
