# Harness

Claude Code's skills, settings, and this file are generated by home-manager from ~/dotfiles, a public repo. The harness is changed by editing that repo, from whichever project the friction showed up in.

- A skill is `~/dotfiles/home/claude/skills/<name>/SKILL.md`. `~/.claude/skills` is a symlink farm from the nix store; never write there.
- The flake sees tracked files only, so a new directory must be `git add`ed before a build or switch can pick it up.
- Configs are keyed by hostname, so `home-manager switch --flake ~/dotfiles` and `sudo darwin-rebuild switch --flake ~/dotfiles` pick this machine's config without a `#name`.
- From a session in another project, changes to ~/dotfiles stop at writing files. Do not run `git add`, `git commit`, `home-manager switch`, or `darwin-rebuild` there; print the commands for the user, the way a push waits for an explicit ask.
- Keep project names, work hostnames, and key filenames out of that repo and its commit messages.
- The Bash tool runs bash 5 from nixpkgs (`CLAUDE_CODE_SHELL` in claude.nix), whatever the login shell is. `sed` is GNU sed, so `sed -i` takes no `''` suffix.

# Commits and pull requests

One commit per change. What may happen to a pull request's branch depends on its stage:

- **Draft, not yet reviewed**: reshape your own commits as needed (amend, or fixup and autosquash).
- **Under review** (out of draft, or reviewed): the branch only grows, so each push can be reviewed on its own. A review fix goes on as a new commit, usually `git commit --fixup=<sha>` aimed at the commit it corrects, never at a `fixup!` or `amend!` commit; the address-review skill sets out when it is an `amend!` or a commit of its own instead. The one exception to growing: a fixup of your own that no one has reviewed yet is corrected in place (amend or fold, as address-review sets out) rather than by another fixup, since a fixup is what a reviewer reads to see what changed since their last look; the author then pushes with `git push --force-with-lease`. Never amend, rebase, or force-push on your own otherwise. A moved base stays as it is unless it conflicts or the change needs what landed; then say so and name `git rb` and `git push --force-with-lease`.
- **Before merge**: the author squashes and catches up with the base in one push: `git fetch origin <base>`, `git rebase -i --autosquash origin/<base>`, `git push --force-with-lease`. Repositories that squash-merge skip this. When the review is settled, say the branch is ready for it and name the commands.

An instruction to keep a pull request to one commit, from an issue for example, covers the draft stage only.

# Causes

A fix that removes the symptom is not finished until the cause is named. Before calling a bug fixed, say in one line what caused it and what evidence says so — a log line, a `git log -S` hit, a failing test, a repro. Where there is no evidence for the step below, stop and call it a hypothesis rather than filling the gap with something plausible. Depth is a result, not a target: keep going down while the evidence holds, and stop at a cause that can actually be changed. When the same failure turns up a second time, the cause to name is why the first fix let it through.
