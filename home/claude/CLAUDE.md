# Harness

Claude Code's skills, settings, and this file are generated by home-manager from ~/dotfiles, a public repo. Change the harness by editing that repo, from whichever project the friction showed up in.

- A skill is `~/dotfiles/home/claude/skills/<name>/SKILL.md`. `~/.claude/skills` is a symlink farm from the nix store; never write there.
- The flake sees tracked files only, so a new file must be `git add`ed before a build or switch can pick it up.
- Which command applies a change depends on where it is: `home/` (this file and skills included) takes `home-manager switch --flake ~/dotfiles`, `hosts/` takes `sudo darwin-rebuild switch --flake ~/dotfiles`. nix-darwin installs home-manager but does not activate the home config, so `darwin-rebuild` alone never applies a `home/` change. Print only the command the change needs. The hostname picks the config, so no `#name`.
- File tools refuse writes outside the working directories (`blockWritesOutsideWorkingDirectories` in claude.nix). From a session in another project, ask the user to run `/add-dir ~/dotfiles` before editing there; do not write the files through Bash instead.
- From a session in another project, changes to ~/dotfiles stop at writing files: print the `git add`, `git commit`, and switch commands for the user instead of running them.
- Keep project names, work hostnames, and key filenames out of that repo and its commit messages.
- A rule about how to work that holds in every project belongs here or in a skill, not in a project's memory: of a project's memory only the `MEMORY.md` index loads at the start of a session, and the notes it points to are read only when Claude goes looking, so a rule kept there rarely changes what Claude does. When the user corrects something of that kind, say so and suggest `/retro`.
- The Bash tool runs bash 5 from nixpkgs (`CLAUDE_CODE_SHELL` in claude.nix), whatever the login shell is. `sed` and the coreutils (`head`, `timeout`, `date`, `stat`, and the rest) are GNU, so `sed -i` takes no `''` suffix and `head -c -1` works; `python3` is nixpkgs', not macOS's 3.9. `awk` is still macOS's, and `find` and `grep` are Claude Code's own wrappers.

# Commits and pull requests

These are defaults. Where a repository sets its own git workflow, in its CLAUDE.md, CONTRIBUTING, or a contract either points to, follow the repository, and fall back to this section only on what it leaves unsaid. Instruction files are concatenated rather than layered, so this line is what settles a conflict between them.

One commit per change. What may happen to the branch depends on its stage:

- **No pull request yet**: fold work into the commit it belongs to (amend, or a fixup folded in with `git squash-fixups`), without asking. `git squash-fixups` keeps the base where it is and moves the branches of a stack along; never autosquash onto a local `main`, which may have moved.
- **Draft, not yet reviewed**: reshape your own commits the same way, as needed.
- **Under review** (out of draft, or reviewed): the branch only grows. A review fix is a new commit, usually `git commit --fixup=<sha>` of the commit it corrects, never of a `fixup!` or `amend!`; address-review sets out when it is an `amend!` or its own commit. Amend or fold an unreviewed fixup of your own in place, then push it with `git push --force-with-lease`. Do not otherwise amend, rebase, or force-push on your own. A moved base stays unless it conflicts or the change needs what landed; then say so and name `git rb` and `git push --force-with-lease`.
- **Before merge**: the author squashes the fixups onto the same base, `git squash-fixups <base>`, and pushes with `git push --force-with-lease`, so the diff the reviewers approved stays the same. Catch up with the base only when it conflicts or the repository requires an up-to-date branch. Repositories that squash-merge skip this. When the review is settled, say the branch is ready for that.

An instruction to keep a pull request to one commit, from an issue for example, covers the draft stage only.

# One pull request per session

A session holds one pull request, so that only that session's review handling and Auto-fix write to it. When work splits into more than one PR, for whatever reason (a split for review, a repository rule that keeps some changes such as CI permissions in a PR of their own, a stack), keep one PR here and hand each other PR to a session of its own as it is about to be opened, with its branch and what it is for: in the desktop app, `start_session`, or `hand_off_to_session` for the task in flight; elsewhere, tell the user which PR is left to open. A PR this session opened or bound before handing it over is `unbind_pr`ed here, so that this session's Auto-fix stops pushing to it. A PreToolUse hook denies a command that opens two PRs, and `gh pr create` in a session whose earlier PR is still open.

A session can still end up holding more than one, such as a fork, which inherits every binding of the session it came from (`get_status` reports them as `inherited`). Split them the same way: keep the PR this session is for and `unbind_pr` the others. The session it came from keeps its bindings, the PR this session kept included: ask it with `SendMessage` to unbind that PR, and when that cannot be done, tell the user in one line which session still holds which PR.

# Steps and questions for the user

Write every reply, status line included, in the language of the user's latest message, not that of the files, tool output, or instruction files in view. When that message has no words of its own, such as a slash command with only a URL, keep the language of the user's earlier messages. A Stop hook sends a reply back when the user's latest message is Japanese and the reply is not.

Before a run of three or more tool calls, such as an investigation, say in one line what you are checking, and again when the focus moves; the user sees only the text you write, and a run of tool calls without any reads as a stall. Batch independent reads into one call. For a fact that would not change the conclusion, search once, and when it is not found, say it is unverified and go on. To read several files of another repository, make a shallow clone of the tag in the scratchpad and search it, rather than fetching the files one at a time through an API.

Steps left for the user to run, such as landing, pushing, applying a configuration, a check on another machine, or a cleanup, go out as the exact commands in the order to run them, one fenced block each. Name the directory or machine when it is not the current one. Never stand in for a command with "the usual steps" or an alias named without its invocation: the user runs them from the reply, not from memory.

Ask a question once. When the user answers something else and does not take it up, do not ask it again, in the reply or in a closing prompt; say once that it is still open, then leave it until they come back to it.

# Comments, commit messages, and PR descriptions

A comment is for whoever reads the code as it stands: a constraint, an invariant, a non-obvious trade-off, or why a value is what it is. A commit message is for whoever reads the change: why it was needed and why this approach. If a sentence still matters once the commit is out of view, it is a comment; if it only explains the patch, it is the message. Skip comments that restate the code.

An overview, such as a file's header comment, a PR description's summary, or a section heading, says what each part is for. How it works and the exact values go next to the code that does it, or a level below the overview. A term the reader has not met yet, such as an argument or an internal name, is explained before or where it is first used. When two things share a name, such as a field and a method both called `Fetch`, name each with its owner at first mention (`Client.Fetch`, the service's `Fetch`) and keep the qualifier after, in a reply as much as in a comment.

A comment, commit message, or PR description covers only what its change does. A decision about later or separate work, such as a task still to come and what it will need, goes in the issue that owns that work.

In Japanese, in replies as much as in code, issues, and PRs, use the word Japanese engineers use, not a word-for-word rendering of the English, which makes the reader translate it back: 通知, not 知らせ; 発火する, not 鳴る; バージョン, not 版. A verb or a metaphor can be a calque as much as a one-character noun. When unsure, take the word the vendor's Japanese documentation uses, or keep the English term (severity).

# Causes

A fix that removes the symptom is not finished until the cause is named. Before calling a bug fixed, say in one line what caused it and what evidence says so — a log line, a `git log -S` hit, a failing test, a repro. Where there is no evidence for the step below, stop and call it a hypothesis rather than filling the gap with something plausible. Keep going down while the evidence holds, and stop at a cause that can actually be changed. When the same failure turns up a second time, the cause to name is why the first fix let it through.

The same holds for any claim that leaves the session, in a reply, a generated page, or memory. What code does or what a value means rests on the code and the values at its real call sites, not on the shape of a signature; what a spec or issue says, on its text; a state such as which points were commented on, merged, or approved, on the PR or issue read just now, not on a remark about it. A summary of earlier work, such as the one compaction leaves, is a remark too: re-read the state before stating it. What you have not read, call unverified.

# Showing changes

Every time you change files, show the diff itself, not only a summary of it. In the desktop app, open the diff pane for files in the session's folders; for anything else, paste `git diff` in a `diff` code block. Show it before asking the user to commit or push.
